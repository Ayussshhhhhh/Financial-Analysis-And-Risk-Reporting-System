# Deployment and refresh guide

## Local SQL Server

1. Restore AdventureWorksDW in SQL Server and create EnterpriseBI with scripts `01`–`10`.
2. Run `EXEC stg.usp_LoadFromAdventureWorksDW; EXEC mart.usp_BuildCurated;` or `EXEC audit.usp_RunRefresh;`.
3. Inspect `audit.PipelineRun` and run `04_data_quality_checks.sql` plus `tests/sql_validation_tests.sql`.
4. Connect Power BI Desktop to `EnterpriseBI`; use Windows or managed service credentials appropriate to the environment. Do not store passwords in a PBIX or source control.

## Power BI Desktop model and publish

1. Create the model and pages described in `power_bi/semantic_model.md` and `power_bi/dashboard_specification.md`; define measures in `power_bi/dax_measures.md`.
2. Configure RLS roles and validate **View as** with sample identities; see `power_bi/rls_configuration.md`.
3. Save `power_bi/enterprise_bi_suite.pbix`. The binary is not generated by this source repository because Power BI Desktop is required.
4. Publish to a restricted workspace. Use Entra groups rather than individual users in production. Keep HR/finance models in separate workspaces as required by policy.
5. In semantic model settings, set gateway connection and credentials using the approved gateway service account. Configure refresh cadence within tenant capacity/license limits; test manually before enabling schedule.
6. Assign users/groups to workspace/app and semantic-model RLS roles. Workspace Admin/Member/Contributor roles can have elevated data access; regional managers should generally be app consumers.
7. Verify refresh history after each run, configure failure notifications, and compare totals to SQL reconciliation. Configure data alerts only on supported pinned dashboard card visuals.

## Local scheduled equivalent

Use SQL Server Agent with a least-privilege proxy/credential and a daily schedule. Execute `EXEC audit.usp_RunRefresh;` then QA procedure/query; fail the job if exceptions exist. See `azure_data_factory/sql_agent_job.md`. For Power BI refresh, use gateway schedule or manual Desktop refresh in a service-free demo. Record the demo only in an authorized environment; do not claim a simulated publish as an actual deployment.

## Azure Data Factory migration

Use a self-hosted integration runtime for on-prem SQL Server, parameterized linked service, datasets for source facts and staging destinations, copy activity, validation stored procedure, curated-load stored procedure, and success/failure branches. Configure retries (for transient connectivity only), secure inputs/outputs, Key Vault-backed secrets, trigger schedule, diagnostic settings, alert rules, and run monitoring. See `azure_data_factory/pipeline_design.md`.

## Licensing and availability

Power BI Service sharing and scheduled refresh depend on tenant configuration, capacity, and licensing. Confirm current requirements with the tenant administrator before publication. If a tenant is unavailable, retain the local model/report and follow this checklist during a recorded demonstration; screenshots and recordings must be captured from an actual environment and are not included as fabricated evidence.

## Known limitations

- SQL Server and Power BI Desktop/Service are not available inside this repository workspace; no binary report, screenshots, real run logs, or actual cloud configuration is claimed.
- AdventureWorksDW variants have column and inventory-table differences. Validate source schema; script 03 supports the standard FactInternetSales columns and requires adjustment for nonstandard releases.
- Source sales sample primarily provides internet sales. Reseller sales and finance measures need separate loads.
- Sample database does not offer a suitable monthly HR event dataset, approved targets, operating expenses, or currency exchange rates. The HR table is an empty schema contract; it has no fabricated values.
- Full reload is the baseline. Incremental loads require change capture/watermark design and late-arriving record validation.
